# 本机 100 并发请求测试

测试时间：2026-09-17 20:13（北京时间）；2026-09-18 整理。主代理顺序运行真实求解与真实截图识别，每项一次100请求、并发100，不自动重试拒绝请求。

## 环境与输入

- Windows build 26100，Python 3.11.5，16个逻辑CPU，内存16,342,138,880字节；CPU具体型号未取得。
- HTTP环回直连 `127.0.0.1:8000`，无Caddy、TLS或带宽模拟；API已运行并处理过任务，非冷启动测试。
- 一个API进程、两个计算进程、八个排队位置、两个上传槽位。求解限3秒/300000节点，识别限25秒。
- 本次没有应用Compose中的2 CPU/2 GiB容器限制。
- 求解：人工整理的5×5外圈16可放格，升力1、2、3、6各三个。识别：用户原始截图，1,103,648字节；没有用伪造图片替代。

## 结果

| 指标 | 求解 | 图片识别 |
| --- | ---: | ---: |
| 提交请求 | 100 | 100 |
| 接收202 | 65 | 2 |
| 繁忙拒绝429 | 35（QUEUE_FULL） | 98（UPLOAD_BUSY） |
| 成功结果 | 65 solved | 2 draft |
| 传输错误/其他HTTP错误/轮询错误 | 0 / 0 / 0 | 0 / 0 / 0 |
| 所有提交响应p95 | 422 ms | 563.75 ms |
| 已接收任务端到端p95 | 1,356 ms | 7,823.35 ms |
| 服务进程树RSS采样峰值 | 106.4 MiB | 586.2 MiB |
| CPU采样峰值（一核100%） | 77.48% | 218.75% |
| 健康检查 | 2次均200 | 15次均200 |
| 健康检查最大延迟 | 640 ms | 375 ms |

接收数量受请求到达节奏、上传槽位和完成任务释放容量影响，不是固定容量。求解过程中任务较快完成，所以累计接收数可以超过同时计算加排队的上限10。

**该结果验证了过载保护，不证明能同时服务100个识别用户。** 识别突发中98个请求需要用户稍后重试。两个被接收的请求完成了识别草稿，仍需手动校正，不等于识别自动生成完整正确题目。

首版保留两个计算进程与两个上传槽位。若要提高突发接收率，需要在真实服务器上逐步调整上传槽位并复测；提高上传槽位不能消除OCR吞吐限制。未测E5服务器、20 Mbps公网线路、最大尺寸图片持续负载，不能据此承诺8G服务器能满足任何100并发场景。

## 统计限制

服务PID及其子进程单独采样，不含负载程序。RSS求和可能重复计算共享页，250 ms采样可能漏过短暂峰值。CPU只累计连续采样均出现的同一进程的正增量，新子进程首次采样之前以及退出前未采到的CPU时间可能遗漏。端到端时间包含上传、排队及轮询间隔；分位数只针对被接收并观察到终态的任务。健康检查数量有限。
